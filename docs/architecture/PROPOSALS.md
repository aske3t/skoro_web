## Открытые

### P-22 🟢 Cache-заголовки при записи auth-cookie (`@supabase/ssr` 0.12)
- **Факт.** В 0.12 `setAll(cookies, headers)` передаёт вторым аргументом `Cache-Control: private, no-cache, no-store…`, `Expires: 0`, `Pragma: no-cache`. Библиотека требует ставить их на ответ, чтобы CDN не закэшировал чужую сессию. В `lib/supabase/middleware.ts` и `server.ts` `headers` не используется: TASK-003 §4.2 запрещает менять поведение.
- **Риск.** Низкий: после TASK-003 middleware работает только на динамических `/dashboard`, `/login` и `/auth`, а Next ставит им `no-store`.
- **Предложение.** В middleware добавить `Object.entries(headers).forEach(([k, v]) => response.headers.set(k, v))` — две строки, по примеру из документации ssr. Можно в TASK-005.

### P-23 🟢 Битая ссылка в Footer на удалённую секцию
- **Факт.** «Our partners → Only Quality» ведёт на `/#reviews`, а секция `Reviews` удалена в TASK-002. Ссылка «Info → Cross city delivery» вела на `/tracking`; в TASK-003 она перенаправлена на `/#services`, чтобы выполнить критерий `grep`. Текст не менялся.
- **Вопрос владельцу.** Куда ведёт «Only Quality» (у остальных партнёров внешние сайты)? Нужна ли колонка «Info» с одной ссылкой-дублем?
- **Итог (владелец, 2026-10-30, `9ed215d`):** футер переписан; «Only Quality» — текстом без ссылки, колонки «Info» и ссылок на `/#reviews` и `/#services` больше нет. Можно закрыть.

### P-24 🟢 `/dashboard` без `NEXT_PUBLIC_SUPABASE_*` отдаёт 500
- **Факт.** `lib/supabase/server.ts` создаёт клиент с `process.env…!`. Без публичных ключей `createServerClient` бросает исключение: `Your project's URL and Key are required…`. Лендинг после TASK-003 от этого не зависит (проверено: `/` → 200).
- **Предложение.** По правилу ленивых env (CURRENT §2) отдавать понятную страницу ошибки ЛК вместо 500. Можно в TASK-005.

### P-25 🟢 Логотип перекрывает пилюлю «Для бизнеса»

- **Варианты.**
  - (а) Убрать пилюлю: после P-08 аудитория одна, кнопка ничего не переключает. Рекомендую.
  - (б) Сдвинуть её правее логотипа: меню станет теснее.
- **Нужно решение** архитектора или владельца — это изменение дизайна шапки.

### P-28 🟠 Telegram-бот с действиями для курьеров: «Взять» / «Отклонить»
- **Запрос владельца (2026-10-13).** Уведомление о новом лиде приходит с двумя кнопками для курьера: **взять** и **отклонить**.
- **Факт.**
  - Сейчас бот только отправляет сообщение: `notify.ts`, `fetch` → `sendMessage`, через `after()`. Входящих запросов от Telegram сайт не принимает.
  - `leads.status`: `new / in_progress / done / spam`. Поля «кто взял» нет.
- **Предложение по реализации** (в рамках ADR-0003, без нового сервиса и зависимостей):
  1. `sendMessage` с `reply_markup.inline_keyboard`: `callback_data` = `take:<lead_id>` / `decline:<lead_id>` (≤ 64 байт, uuid помещается).
  2. **Route Handler** `POST /api/telegram/webhook`:
     - проверка заголовка `X-Telegram-Bot-Api-Secret-Token` (новый секрет `TELEGRAM_WEBHOOK_SECRET`);
     - обработка `callback_query`;
     - запись через admin-клиент;
     - `answerCallbackQuery` + `editMessageText`/`editMessageReplyMarkup` («Взял: Иван, 14:32», кнопки убираются).
  3. **Гонка «двое нажали одновременно»** — условный `update … where id = $1 and status = 'new'`: побеждает первый, второй получает «Уже взят».
  4. **Кто может нажимать** — allowlist Telegram `user_id` курьеров (таблица `couriers` или env). Нажатие чужого — отказ.
  5. **Миграция `leads`:** `assigned_courier`, `taken_at`, плюс статусы по ответам ниже.
  6. **Регистрация вебхука** (`setWebhook`) — для прода. Для Preview — отдельный тестовый бот, иначе Preview перехватит вебхук боевого.
- **Нужно решение:**
  - Куда приходят лиды: в общий чат курьеров (кто первый нажал) или каждому лично?
  - Что значит «отклонить»: курьер отказался и лид остаётся доступен другим, или лид отклонён совсем (`spam` / новый статус `declined`)?
  - Заявки типа «вопрос» (`kind = question`) тоже идут курьерам с кнопками или только менеджеру без кнопок?
  - Связь с заказами: «взятый» лид становится заказом (`orders`) — сейчас или после TASK-005?
  - Отдельная задача (TASK-00X) или часть TASK-005?

### P-29 🟠 Новая интеграция: транзакционные письма клиентам через Resend
- **Запрос владельца (2026-10-21).** Когда заявку на доставку берут в работу, клиент получает email.
- **Факт (сделано по согласию владельца).**
  - Resend через HTTP API (`fetch`), без новых зависимостей; модуль `src/lib/email/` (`server-only`), env `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_REPLY_TO` читаются лениво.
  - Домен отправки — субдомен `notify.skorouvas.cz` (изоляция репутации от основного домена), регион EU. Ответы клиентов — на `skorodelivery@gmail.com`.
  - Письмо отправляет хендлер кнопки бота после условного update; повтор — `Idempotency-Key`. Сбой письма не откатывает статус и виден в группе.
  - Язык — только чешский; язык письма должен браться из языковой версии сайта, когда появится i18n.
- **Нужно от архитектора:** внести Resend в CURRENT §7 (интеграции) и решить, где в будущем хранить локаль заявки (колонка `leads.locale` при i18n).

### P-30 🟠 Побочные действия бота после записи в БД не переживали сбой
- **Инцидент (2026-10-21, владелец).** Бот был выключен, заявку взяли кнопкой. После запуска бот обработал старое нажатие: статус `in_progress` записался, но `answerCallbackQuery` упал на устаревшем нажатии (`query is too old`) до отправки письма; без `bot.catch` grammY остановил polling. Итог: заявка взята, письма нет, бот не отвечает.
- **Сделано по согласию владельца.**
  1. `answerCallbackQuery` не прерывает обработку; `bot.catch` логирует ошибку, бот продолжает работать.
  2. Факт отправки письма — в БД: `leads.client_notified_at` (миграция `20261021005207`). Решение «слать или нет» принимается только по данным из БД (`clientEmailState`).
  3. Повтор: если письмо не ушло — кнопка «📧 Отправить письмо повторно» под заявкой; повторное нажатие на взятую заявку с пустым `client_notified_at` тоже досылает. Дубль исключён `client_notified_at` и `Idempotency-Key`.
- **Нужно от архитектора.** Закрепить правило для всех побочных эффектов (письма, уведомления курьерам после TASK-005): состояние доставки хранится в БД, обработчик идемпотентен и повторяем. Решить, нужен ли автоматический досыл без людей (Vercel Cron; на Hobby — раз в сутки) или достаточно кнопки.

### P-31 🟠 IČO в заявке на доставку и выбор «Компания / Частное лицо» (расходится с P-08)
- **⚠️ Решение владельца, 2026-10-21 (в обход плана архитектора): реализовано** в `feature/lead-form-fields` (`8b362df`, `fbd0a94`):
  - в заявке на доставку выбор «Компания / Частное лицо», по умолчанию «Компания»;
  - для компании IČO обязательно: контрольная сумма (zod) → запрос в ARES в `submitLead` после rate-limit, таймаут 3 с;
  - фирма не найдена → ошибка поля `not_found`; закрыта (`datumZaniku` или `seznamRegistraci.stavZdrojeRes = HISTORICKY`) → `inactive`; ARES недоступен → заявка принимается, `ico_verified = false`, в Telegram «⚠️ не проверено»;
  - миграция `20261021012451_leads_customer_ico`: `customer_type`, `ico`, `company_name`, `ico_verified`.
- **Архитектору — ревью задним числом:**
  - выбор «Частное лицо» фактически возвращает B2C в заявку (пересмотреть P-08 и CURRENT §12);
  - ARES — новая внешняя интеграция (добавить в CURRENT §7);
  - запросы в ARES не ограничены отдельно: rate-limit считает только сохранённые заявки, поток заявок с неверным IČO тоже ходит в ARES;
  - IČO в профиле ЛК и онбординг (P-21).
- **Исходная постановка вопроса** (до решения владельца):
- **Запрос владельца (2026-10-21).** В заявке на доставку IČO обязательно, если клиент выбрал бизнес-вариант. В форме нужен выбор «Компания / Частное лицо».
- **Конфликт.** По P-08 и CURRENT §12 сайт сейчас только B2B: `/personal` и переключатель аудитории убраны в TASK-003. Выбор «Частное лицо» возвращает B2C-клиентов. Агент не реализовывал до решения архитектора.
- **Факт о проверке IČO.** 8 цифр, 8-я — контрольная: сумма первых семи с весами 8…2, `r = сумма mod 11`, контрольная = 1 при `r = 0`, 0 при `r = 1`, иначе `11 − r`.
  - Ловит опечатки и случайные числа (проходит ~1 из 10 случайных наборов).
  - **Не подтверждает, что фирма существует и активна.**
  - Это даёт только реестр **ARES**: публичный REST без ключа, `GET https://ares.gov.cz/ekonomicke-subjekty-v-be/rest/ekonomicke-subjekty/{ico}` → название, адрес, статус.
- **Предложение.**
  1. Контрольная сумма — всегда, на сервере (zod) и в HTML-ограничениях поля.
  2. ARES — мягкая проверка на сервере: таймаут ~3 с. Фирма не найдена → ошибка поля. ARES недоступен → не блокировать, пометить «не проверено» в Telegram. Название фирмы из ARES сохранять и показывать курьеру и в письме.
  3. Миграция `leads`: `customer_type` (`company`/`person`), `ico`, `company_name`, `ico_verified_at`.
- **Нужно решение:**
  - возвращаем ли B2C (тогда пересмотр P-08: тексты, тарифы, ЛК);
  - где выбор — в форме или «версии страницы» (`/` и `/personal`);
  - нужен ли ARES или достаточно контрольной суммы;
  - связь с онбордингом B2B (P-21: `profiles.company_name`, IČO в профиле ЛК).

### P-35 🟠 Тарифы раздельно для бизнеса и частных лиц (задел под TASK-004)
- **Запрос владельца (2026-10-21).** Тарифная логика в форме — своя для каждой версии сайта (P-32). Пока только подготовка, без изменения поведения.

### P-36 🟠 Заявка как первый контакт: маршрут и сообщение необязательны (редизайн формы)
- **Запрос владельца (2026-10-23).** Редизайн `ContactForm` по critique (`.impeccable/critique/`, P1 «форма просит заказ, а не первый контакт»): маршрут, получатель и фото — под раскрытием «Уже есть конкретная доставка?»; сообщение необязательно при заполненных адресах. Оплата остаётся обязательной.
- **Факт — расходится с кодом и схемой:**
  - `schema.ts`: при `kind = delivery` обязательны `pickupAddress`, `deliveryAddress`, `phone`, `paymentMethod`; `message` обязателен всегда. То же дублирует `client-validation.ts`.
  - БД: `leads.message text not null check (char_length(message) between 1 and 4000)` (`20260929205817_create_leads.sql`). Необязательное сообщение требует миграции.
  - `recipientName`, `recipientPhone`, фото уже необязательны — их можно убрать под раскрытие без изменений сервера.
- **[Предп.] Варианты:**
  - **А.** Под раскрытие только получатель и фото; маршрут и сообщение остаются обязательными. Сервер и БД не меняются.
  - **Б.** А + сообщение необязательно при заполненных адресах: правка `schema.ts`, `client-validation.ts`, тестов и миграция `message` → nullable (или снятие `min 1`).
  - **В.** Б + маршрут под раскрытием и необязателен: заявка `delivery` без адресов. Тогда открыт вопрос, чем она отличается от `kind = question`, и как быть с обязательной оплатой без маршрута.
- **Решение владельца (2026-10-23):** редизайн формы — по варианту А (получатель и фото под раскрытием, маршрут обязателен). Затем отдельно — часть Б: комментарий к доставке необязателен, для `kind = question` текст обязателен.
  - Сделано: миграция `20261023102152_leads_message_optional_for_delivery.sql` (`message` nullable + check `kind <> 'question' or message is not null`), `schema.ts`, `client-validation.ts`, `notify.ts` (без комментария блок сообщения в Telegram не выводится), тесты, форма.
  - Применяет владелец; после неё — перегенерация `src/types/database.ts`.
- **Открыто для архитектора:** контракт заявки изменён без ADR; вариант В (маршрут необязателен) не делали.

### P-37 🟢 Общие проблемы лендинга из разбора секции «Почему мы» (2026-10-28)
Найдены в `/impeccable critique` секции `Services.tsx` (снимок `.impeccable/critique/2026-10-28T11-34-54Z__src-components-sections-services-tsx.md`). Касаются всего сайта, поэтому внутри секции не чинились.

### P-38 🟠 Модель цены мультимаршрута от владельца расходится с калькулятором (вход для TASK-004)
- **Модель владельца (2026-10-28), дословно по смыслу:**
  - База слота — Express 240 / 3 часа 180 / В течение дня 150 Kč; включает 1 забор, 1 доставку и до 10 км маршрута.
  - Каждая доп. точка: +100 (Express) / +70 (3 часа) / +60 (День) Kč.
  - 20 Kč за каждый км сверх 10, итог округляется вверх до 10 Kč.
  - Лимиты: Express — до 3 точек и 10 км; 3 часа — до 5 точек и 25 км; День — до 6 точек и 35 км.
  - Маршрут считается от первого забора до последней доставки, сначала все заборы.
  - Цена никогда не превышает сумму отдельных заказов.
  - За лимитами или за пределами Брно — экран «согласовать лично».
- **Как сейчас в коде** ([Факт], `src/lib/calculator/pricing.ts`, данные Supabase):
  - compare: слот + `skoro_pricing.per_extra_point` (80 Kč) за доп. точку + км × 15 Kč; км всегда 0 — `zone_distances` пуста (P-18, F-8);
  - route: без batch — полная цена слота за каждую точку; batch (≥2 юнита, одна зона и один слот) — слот + `BATCH_PER_EXTRA_STOP` 100 Kč; доплаты вес/выкуп/документы сверху; 3+ юнита — диалог «индивидуально»;
  - `skoro_pricing.base_price` (500 Kč) нигде не используется; лимитов по слотам, км сверх 10, округления и потолка «не дороже отдельных заказов» нет; адрес получателя на цену не влияет.
- **[Предп.] Что нужно для модели:**
  - тарифы в БД (ADR-0004 §1): по слоту — база, цена доп. точки, включённые км, лимиты точек и км; общие — цена км сверх, шаг округления;
  - формула в `src/lib/pricing/` с vitest (ADR-0004 §2), калькулятор берёт превью оттуда (§3);
  - источник расстояния маршрута с порядком «сначала заборы»: зонной матрицы не хватит, нужен маршрутизатор (например, Google Routes API на сервере) — новая интеграция и ключ;
  - признак «за пределами Брно» (геокодер или зона);
  - судьба доплат (вес, выкуп, документы) и batch-правила в новой модели — владелец их не упомянул.
- **Нужно решение архитектора:** включить модель в TASK-004 (схема тарифов, источник расстояний) и порядок: формула до или после редизайна калькулятора.
- **Решение владельца (2026-10-28):** сначала редизайн калькулятора на текущих формулах (сделано, не закоммичено), формула — в TASK-004.
