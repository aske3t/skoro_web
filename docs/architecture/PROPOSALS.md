## Открытые

### P-01 🔴 Ветки и деплой: какой путь у изменений до прода
- **Факт.** В TASK-001 прод назван `variant1`. При этом `origin/variant1` (`ec05ede`) целиком входит в `dev`, а `master` (`df9591e`) отстаёт от `dev` на 13 коммитов и в разработке не участвует. `vercel.json` в репозитории нет.
- **Вопрос.** Каков маршрут `feature/*` → `dev` → `variant1`? Что делать с `master`: удалить, переименовать `variant1` в `main` или сделать `master` продовой? Какие ветки Vercel деплоит в Production и Preview?
- **Предложение.** Одна продовая ветка по умолчанию (`main`), `dev` для интеграции, Preview на каждую `feature/*`.

### P-02 🔴 Источник истины для схемы БД
- **Факт.**
  - В `supabase/migrations/` есть только `create_leads`. Таблицы `orders`, `payments`, `subscriptions` и справочники, RLS-политики и RPC `create_order_for_user` существуют лишь в удалённой БД.
  - `leads` применена владельцем через SQL Editor (проверено: anon получает `42501`), поэтому `supabase_migrations.schema_migrations` о ней не знает.
  - CLI не находит привязку проекта (`Cannot find project ref`): в `supabase/.temp/` нет `project-ref`, типы генерируются с `--project-id`.
- **Риск.**
  - Безопасность ЛК держится на RLS, которую нельзя проверить по репозиторию.
  - Первый же `supabase db push` упадёт на повторном `create table leads`.
- **Предложение.**
  1. `supabase db pull` → baseline-миграция всей текущей схемы.
  2. `supabase migration repair --status applied 20260929205817`.
  3. Дальше все изменения схемы только через файлы миграций.
- **Нужно решение.** Кто и когда делает baseline? Нужен ли отдельный staging-проект Supabase?

### P-03 🟠 Версия Node для проекта
- **Факт.** У разработчика стоял Node 20.12 (EOL с апреля 2026), теперь Node 22.23.3 в `~/.local/node` (без менеджера версий: `fnm.vercel.app` и `raw.githubusercontent.com` из сети владельца недоступны). vitest 5 требует Node ≥ 22.12. В `package.json` нет `engines`, в репозитории нет `.nvmrc`, версия Node в Vercel неизвестна.
- **Предложение.** Зафиксировать Node 22 LTS в трёх местах: `"engines": { "node": ">=22.12" }`, `.nvmrc` с `22`, настройки проекта Vercel.

### P-04 🟠 Уязвимости зависимостей
- **Факт.** `npm audit`: 7 уязвимостей, из них critical в `next` и high в `sharp`, `ws`, `postcss`, `browserslist`. Все закрываются `npm audit fix` без мажорных обновлений.
- **Факт (2026-09-30).** В рабочей копии `feature/contact-form` лежит незакоммиченное обновление `next` `^15.1.3` → `^16.3.7`, предположительно от `npm audit fix --force`. Это **мажорная версия**: в Next 16 меняются соглашения (в т.ч. middleware и `next lint`). Next 16.3.7 уже установлен в `node_modules`, и при запуске он переписал `tsconfig.json` (`jsx: react-jsx`, `.next/dev/types`). Сборка и тесты на нём не проверялись.
- **Предложение.** Отдельная задача: `npm audit fix` без `--force` (остаёмся на 15.x) → `build` → `test` → деплой. Не смешивать с фичами. Переход на Next 16 — отдельное решение с проверкой миграционного гайда.
- **Нужно решение.** Остаёмся на 15.x с патчами или планируем миграцию на 16?

### P-05 🟠 Где живёт серверная логика
- **Факт.** В TASK-001 появился паттерн «Server Action + admin-клиент (`server-only`) + zod». При этом калькулятор и `createOrder` по-прежнему ходят в Supabase прямо из браузера с anon key, а цену заказа считает RPC, код которого не виден (см. P-02).
- **Вопрос.** Делаем ли Server Actions стандартом для всех записей? В частности, переносим ли `createOrder` на сервер с валидацией через zod?
- **Предложение.** Записи — через Server Actions. Чтение справочников можно оставить на клиенте с anon key при подтверждённой RLS.

### P-06 🟠 Лендинг рендерится динамически
- **Факт.** После сборки все маршруты помечены `ƒ` (dynamic), включая `/`. Причина: `Navbar` в корневом layout вызывает `cookies()` / `supabase.auth.getUser()` на каждом запросе. В TASK-001 упомянуто намерение вернуть статическую генерацию.
- **Предложение.** Одно из двух:
  - определять состояние входа в `NavbarClient` на клиенте;
  - вынести Navbar с сессией в layout группы `/dashboard`.

  В обоих случаях `/` становится статическим.
- **Нужно решение.** Какой вариант и в какой задаче?

### P-07 🟠 Единый источник цен
- **Факт.** Цены заданы в трёх местах:
  - хардкод в `Tariffs.tsx` / `Abons.tsx`;
  - константы в `lib/calculator/surcharges.ts` и `BATCH_PER_EXTRA_STOP` (объявлена дважды);
  - таблицы `skoro_pricing` / `delivery_slots`.

  Плюс логика в RPC.
- **Вопрос.** Источник истины — БД? Тогда лендинг и калькулятор читают цены оттуда, а константы уходят в таблицы.

### P-08 🟢 Регистрация и модель клиента (B2B / B2C)
- **Факт.** Signup удалён. Таблица `profiles` (company_name) в UI не используется. Ссылка `/personal` ведёт на 404, форма трекинга — на удалённую `/tracking`.
- **Вопрос.** Как клиент получает аккаунт? Нужен ли раздел `/personal`? Трекинг — в плане или убрать ссылку?

### P-09 🟢 Выбор геокодера
- **Факт.** Калькулятор использует Google Places. Путь через Nominatim (`/api/geocode/search` + `AddressLookupInput`) — мёртвый код.
- **Предложение.** Оставить один геокодер, второй удалить. Если остаётся Nominatim, его rate-limit нужно перенести в БД или KV, как для лидов.

### P-10 🟢 Антиспам формы: доверие к часам клиента
- **Факт.** По A4 time-trap опирается на `startedAt = Date.now()` клиента. Если часы клиента спешат на несколько секунд, быстро заполненная форма может молча отброситься. Метки из будущего я пропускаю.
- **Предложение.** Если honeypot и rate-limit не справятся, выдавать `startedAt` с сервера, подписанный HMAC. Это надёжнее, чем Turnstile, и без UX-потерь.

### P-11 🟢 Качество: линтер и CI
- **Факт.** Скрипт `lint` вызывает `next lint`, но `eslint` не установлен. CI нет.
- **Предложение.**
  - ESLint (flat config, `eslint-config-next`) или Biome — нужен выбор;
  - GitHub Actions: `tsc --noEmit`, `npm test`, `npm run build` на PR в `dev`.

### P-12 🟢 Гигиена репозитория
- **Факт.**
  - В git лежат `supabase/.temp/*` (локальное состояние CLI, меняется при каждом запуске), файл `sr` (дамп вывода генератора типов) и PNG-макеты в корне.
  - Существующие Supabase-клиенты (`lib/supabase/client.ts`, `server.ts`) не типизированы `<Database>`.
- **Предложение.**

  - удалить `sr`;
  - перенести макеты в `docs/`;
  - типизировать клиенты;
  - описать команду генерации типов в README (через временный файл: `>` обнуляет целевой файл при ошибке; уже есть в `CLAUDE.md`);
