## 1. Система и границы

Skoro — курьерская служба в Брно (CZ) для бизнеса и частных лиц. Основной фокус — B2B; раздел для частных лиц вернулся решением владельца (P-31, P-42). Веб-приложение — это одновременно маркетинговый сайт и рабочий инструмент. Состоит из:

- лендинга (версии «бизнес / частное лицо») с калькулятором и страницами услуг;
- приёма заявок и подписки на рассылку;
- служебного Telegram-бота: заявки, позже заказы и курьеры;
- личного кабинета клиента: заказы, абонемент, платежи.

В плане — оплата онлайн.

Один деплоймент Next.js на Vercel и один проект Supabase, общий для прода и всех Preview (ADR-0002, дополнение). Отдельного бэкенда нет и не планируется. Серверная логика живёт в Server Actions и Route Handlers Next.js, транзакционная — в функциях Postgres.

```mermaid
flowchart LR
  U[Браузер] -->|HTTPS| APP["Next.js 15.5 · Vercel"]
  U -->|publishable key: вход, справочники калькулятора| SB[(Supabase<br/>Auth + Postgres)]
  APP -->|server client: сессия, RLS| SB
  APP -->|admin client: secret key, server-only| SB
  TGS[Служебный бот] -->|webhook /api/telegram/dispatch| APP
  APP -->|карточки заявок и заказов, кнопки| TGS
  TGC[Клиентский бот] -->|webhook /api/telegram/client| APP
  APP -->|вход, меню, Mini App, статусы клиенту| TGC
  APP -->|письма клиентам| RS[Resend]
  SB -->|письма Auth через SMTP| RS
  APP -->|проверка IČO| ARES[ARES]
  U -->|Places API| GM[Google Maps]
```

Отклонения от правил сейчас:
- калькулятор читает справочники из браузера — уберёт TASK-004;
- заказ создаётся RPC из браузера — уберёт TASK-005.

**Сквозные правила:**

- **Валидация** — zod, только на сервере. zod не попадает в клиентский бандл: клиентские константы лежат в отдельном `constants.ts`.
- **Ошибки** возвращаются кодами, тексты для пользователя живут в UI.
- **Env** читаются лениво. Отсутствие ключа ломает фичу, а не рендер страницы или сборку. Серверные ключи — без `NEXT_PUBLIC_`.
- **Бизнес-время** — `Europe/Prague`, считается на сервере. Время из `datetime-local` трактуется как пражское, где бы ни был браузер.
- **Побочные эффекты** (письма, уведомления, правка сообщений) выполняются через `after()` или после записи, не откатывают основную операцию. Факт выполнения хранится в БД (`client_notified_at` и т. п.). Обработчик идемпотентен, повтор — кнопкой. Автоматический досыл (cron) пока не нужен (P-30).
- **Миграции совместимы с `main`** (ADR-0002, дополнение).
- **Юридические тексты** (политика, согласия, условия) исполнитель пишет и меняет только по прямой команде владельца.

## 3. Слои и модули

| Слой | Где | Правило |
|---|---|---|
| Маршруты | `src/app/**` | RSC по умолчанию. `"use client"` — только для интерактива |
| UI | `src/components/**` | Не ходит в БД сам. Получает данные пропсами или вызывает action |
| Домен | `src/lib/<domain>/` | Чистые функции и actions домена. Зависимости направлены вниз: UI → domain → infra |
| Инфраструктура | `src/lib/supabase/*`, `src/lib/maps/*`, `src/lib/email/resend.ts` | Фабрики клиентов, внешние SDK и API |
| Типы БД | `src/types/database.ts` | Только генерация, руками не правится (исключение — временно до применения миграции, с пометкой в STATE) |

**Доменные модули:**

| Модуль | Что делает |
|---|---|
| `lib/leads/` | Заявки: схема, ARES, телефон, фото, антиспам, уведомление. **Эталон** для новых доменов |
| `lib/newsletter/` | Подписка из футера (P-40) |
| `lib/telegram/` | Служебный бот (корень) и клиентский бот (`client/`, ADR-0006 §4); общий код — в корне. Внутри модуля — относительные импорты с `.ts` (скрипты без бандлера) |
| `lib/email/` | Письма клиентам через Resend |
| `lib/pricing/` | Только чистые функции цены (ADR-0004) |
| `lib/calculator/` | Формулы калькулятора до TASK-004 и оценка конкурентов |
| `lib/orders/` *(ADR-0006)* | Заказы: пражское время и слот, `submitOptionOrder`, статусы, запросы |
| `lib/options/forms/` *(ADR-0006)* | Реестр видов форм опций (пилот — `city_delivery`) |
| `lib/pricing/tariffs/` *(ADR-0006)* | Реестр видов тарифов (пилот — `slot_table`, `flat`) |

Шаблон доменного модуля:

```
lib/<domain>/
  constants.ts   client-safe константы и типы (без zod)
  schema.ts      zod-схемы, нормализация; server-side
  actions.ts     "use server"; validate → authorize → persist → after()
  *.ts           чистая логика и доступ к данным
  *.test.ts      vitest на чистые функции
```

**Supabase-клиенты** (ADR-0003):

| Клиент | Ключ | Где | Назначение |
|---|---|---|---|
| `lib/supabase/client.ts` | publishable | client components | Вход и выход; калькулятор до TASK-004 |
| `lib/supabase/server.ts` | publishable + cookie | динамические RSC, actions, route handlers | Всё от имени пользователя, RLS действует |
| `lib/supabase/admin.ts` | secret, `server-only` | actions, route handlers, бот | Системные записи (лиды, подписка, бот) и внутренние SQL-функции **после** явной проверки прав в коде |

## 6. Ключевые потоки

**Заявка (эталон).**
1. `ContactForm` → `submitLead`.
2. honeypot и time-trap → zod → rate-limit по `ip_hash` → ARES для компании.
3. Запись через admin-клиент.
4. `after()`: сообщение в группу «Заявки» с кнопками (и фото ответом).
5. Админ нажимает «Взял в работу» → условный update → письмо клиенту (Resend) → правка сообщения.

**Заказ клиента (пилот бота, ADR-0006 §6–§7).**
1. Клиентский бот → Mini App формы опции → `submitOptionOrder`: `initData` → контакт → клиент → опция → zod вида формы → слот по Europe/Prague → тариф опции.
2. Admin-клиент вызывает `create_option_order` — атомарно, со снимком формы и цены.
3. `after()`: служебный бот шлёт карточку в «Заявки» с кнопками «Принять / Отклонить», затем «Доставлен»; клиентский бот — подтверждение клиенту.
4. Статусы: клиенту — сообщение клиентского бота и письмо; факт отправки — в `notifications`.
5. Веб-кабинет (переписанная TASK-005) станет вторым каналом той же функции с `created_via = 'web'`.

**Калькулятор (сейчас).** Справочники читаются из браузера, формулы — `lib/calculator`. После TASK-004 — модель P-38 через `lib/pricing`.

**Оплата (цель, TASK-006).** Сумма считается только на сервере. Статус меняет только вебхук провайдера. Перед этой задачей — отдельный staging-проект Supabase.

**Релиз `dev` → `main`** — по команде владельца:
1. Перед PR: `grep -rn "TODO(владелец)" src` — плейсхолдеры, видимые на сайте, заполнены или скрыты (P-41); миграции из `dev` применены.
2. PR `dev` → `main`, CI зелёный, Merge. Vercel сам пересобирает прод.
3. Смоук на `skorouvas.cz`: главная, калькулятор, тестовая заявка → Telegram, вход → кабинет.
4. Откат: Vercel → Deployments → предыдущий продакшен-деплой → Instant Rollback; затем revert-PR в `main`.
5. Contract-миграции следующей задачи — только после шага 3.

Прямые PR в `main` в обход `dev` (как PR #6) не делаются: после них `main` и `dev` расходятся.
