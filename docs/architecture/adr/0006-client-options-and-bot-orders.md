# ADR-0006: Опции клиента, тарифы, формы и заказы через Telegram

- **Статус:** принято, 2026-11-02; уточнено в тот же день (вход по приглашению вместо номера телефона, регистрация вне пилота); **изменено 2026-11-05 (P-43): два бота — служебный и клиентский** (§4, §5, §6, §7, §8)
- **Заменяет:** в ADR-0005 — §1 в части `client_prices` и §3 в части сигнатуры функции заказа (см. «Изменение 2026-11-02» там)
- **Связано:** ADR-0002 (миграции, дополнение), ADR-0003 (серверный путь записи), ADR-0004 (цены), ADR-0005 (кабинет)

## Контекст

Решения владельца от 2026-11-02:

1. **У клиентов есть интерфейс в Telegram.** Клиент входит прямо в боте. Регистрация — позже, по аналогии с кабинетом: клиентов заводит владелец (уточнение того же дня). С 2026-11-05 клиентский интерфейс — **отдельный бот**, а нынешний бот остаётся служебным (P-43, решение владельца).
2. **Поля заказа в боте те же, что в форме на сайте.** Сайту нужно поле «время доставки».
3. **У клиента несколько опций (услуг) с разной тарификацией.** Состояние хранится в БД отдельно для каждого клиента. Опции бывают уникальные для клиента и общие (например, «Доставка по городу»), но тариф у общей опции свой у каждого клиента.
4. **У каждой опции своя форма.**
5. **Клиенту приходят уведомления о статусах**, включая «доставка выполнена».
6. **Пилот:** два клиента, данные вносятся в БД вручную, одна опция — «Доставка по городу».

TASK-005 (кабинет) не начата. Модель `client_prices` (точка × слот) из ADR-0005 — частный случай нового тарифа одной опции. Строить её отдельно значило бы переделывать.

## Решение

### 1. Данные

| Таблица | Что это | Кто пишет |
|---|---|---|
| `clients` | Клиент (как в ADR-0005). `status`: `pending` (заявка из бота) / `active` / `blocked` вместо булева `active` | владелец; `pending` — сервер при регистрации |
| `client_contacts` | Люди клиента, которые могут заказывать: имя, телефон (E.164), email, `telegram_user_id` (unique, null), `status`, `invite_token_hash`, `invite_expires_at` | владелец; сервер при приглашении и входе |
| `client_locations` | Точки клиента (как в ADR-0005) | владелец |
| `telegram_users` | Все, кто писал любому из ботов в личку: `telegram_user_id` pk, имя, username, `last_seen_at`. Telegram id один и тот же для обоих ботов | сервер (боты) |
| `service_options` | Каталог опций: `slug` (unique), название, описание, `form_kind`, `client_id` (null — общая, иначе уникальная опция клиента), `active`, порядок | общие — миграцией; уникальные — владелец |
| `client_options` | Опции, подключённые клиенту: `client_id`, `option_id`, своё название (необязательно), `tariff_kind`, `tariff_params jsonb`, `form_defaults jsonb` (предзаполнение, например фиксированная точка забора), `active`, порядок; `unique (client_id, option_id)` | владелец |
| `notifications` | Факт отправки уведомлений: `entity` (`lead` / `order`), `entity_id`, `event`, `channel` (`telegram` / `email`), получатель, `sent_at`, `last_error`, `attempts`; `unique (entity, entity_id, event, channel)` | сервер |
| `bot_sessions` | Хранилище `session()` grammY: `key` (с префиксом бота, например `client:<chat_id>`), `value jsonb`, `updated_at` | сервер (боты) |

- **Уникальную опцию можно подключить только её клиенту.** Это гарантирует триггер.
- **Данные клиентов не попадают в репозиторий** — он публичный. Миграцией заводится только общий каталог, в пилоте одна строка: `city_delivery` / «Доставка по городу». Клиенты, контакты, точки и тарифы вносятся SQL-сниппетами из `docs/ops/clients.md` с подстановкой значений.
- **Все новые таблицы — только для сервера:** RLS включён, политик нет, `revoke all` у `anon` и `authenticated`. Политики чтения для кабинета добавит веб-часть TASK-005.

### 2. Тарифы

Тариф опции = **вид** (`tariff_kind`, код) + **параметры** (`tariff_params`, данные).

- Виды — реестр чистых функций в `src/lib/pricing/tariffs/`. У каждого вида: zod-схема параметров и `quote(params, request, context) → Quote | ошибка`.
- **Пилот — `slot_table`:**
  - параметры: `{ "default": { "<slug слота>": цена, … }, "byLocation": { "<uuid точки>": { "<slug слота>": цена } } }`, `byLocation` необязателен;
  - порядок поиска: точка × слот → `default` × слот → `delivery_slots.base_price` (ADR-0004).
- **Второй вид для проверки реестра — `flat`:** `{ "price": число }`.
- **Будущие виды** (модель P-38 с километрами, процент от выкупа и т. п.) добавляются кодом. Схема БД при этом не меняется.
- **Параметры проверяются zod при каждом расчёте.** Битый JSON в БД → код `tariff_invalid`, заказ не создаётся, админ получает сообщение в группе.

### 3. Формы

Форма опции = **вид формы** (`form_kind`, код) + предзаполнение (`form_defaults`, данные).

- Виды — реестр в `src/lib/options/forms/`. У каждого вида:
  - список полей (тип, обязательность, подпись);
  - zod-схема;
  - функция «данные формы → запрос к тарифу»;
  - форматтер для Telegram и письма.
- **Пилот — `city_delivery`.** Поля — как в блоке доставки на сайте:
  - откуда: точка клиента или адрес;
  - куда;
  - получатель: имя и телефон;
  - **время доставки**: «как можно скорее» или конкретное время по Праге;
  - комментарий;
  - фото.

  Оплата берётся из клиента и в форме только показывается. Правила валидации полей **импортируются** из `lib/leads` (телефон, адрес, фото), а не копируются.
- **Новая уникальная опция** либо переиспользует существующий вид формы со своим `form_defaults`, либо получает новый вид кодом.

### 4. Каналы

**Два бота, общий сервер и БД** (P-43, решение владельца 2026-11-05). Сообщениями в Telegram боты не обмениваются. Каждый получает свои обновления и шлёт свои сообщения, связь между ними — через БД и серверный код.

| | Служебный бот (нынешний) | Клиентский бот (новый) |
|---|---|---|
| Кто пользуется | админы; позже курьеры | клиенты и гости |
| Где | группа «Заявки» и личка админа | только личка; добавление в группы выключено |
| Что делает | карточки заявок и заказов с кнопками, `/invite`, сообщения о подключении клиентов, повтор уведомлений | вход по приглашению, меню, «Новый заказ» (Mini App), «Мои заказы», уведомления клиенту о статусах |
| Токен, секрет вебхука | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` — без изменений | `TELEGRAM_CLIENT_BOT_TOKEN`, `TELEGRAM_CLIENT_WEBHOOK_SECRET`, `TELEGRAM_CLIENT_BOT_USERNAME` (для ссылок-приглашений) |
| Вебхук | `/api/telegram/dispatch` — без изменений | `/api/telegram/client` |
| Код | `src/lib/telegram/` — как сейчас | `src/lib/telegram/client/` |
| Профиль | служебный, как сейчас | клиентский: имя, описание, аватар Skoro |

- **Нажатие кнопки получает только бот, который отправил сообщение, и только он может это сообщение править.** Поэтому карточку заказа шлёт и обрабатывает служебный бот, а клиенту пишет клиентский. Кнопки под старыми заявками продолжают работать.
- **Общий код** — в корне `src/lib/telegram/`: HTML-экранирование, проверка секрета вебхука, разбор `initData`, токены приглашений, отправка сообщения через Bot API с выбором бота. Внутри модуля — относительные импорты с `.ts`, как сейчас.
- **Чат клиентского бота** — вход по приглашению, меню, выбор опции, подтверждения, «Мои заказы», уведомления о статусах. Состояние коротких шагов хранится в БД: встроенный `session()` grammY с адаптером на `bot_sessions`. Плагины grammY не подключаются.
- **Формы заказа — Telegram Mini App:** страницы сайта `/tg/*`, открываются кнопкой `web_app` клиентского бота.
  - Это те же веб-компоненты, что в форме заявки (`AddressInput` с подсказками Google, `PhoneInput`, `PhotoField`, `IcoField`). Позже — и в кабинете.
  - Пошаговая анкета в чате не делается: адрес без подсказок, фото и дата текстом — хуже по удобству и дублирует логику.
- **Подлинность Mini App:**
  - Server Action получает `initData`;
  - проверяет HMAC **по токену клиентского бота** (по документации Telegram «Validating data received via the Mini App»);
  - проверяет свежесть `auth_date` (не старше 24 часов);
  - находит `telegram_user_id` → активный контакт → активного клиента.

  Без этого запрос отклоняется. Supabase-сессия для Mini App не нужна.
- **Роли проще, чем в одном боте:** служебный бот знает только админов (`TELEGRAM_ADMIN_IDS`), позже курьеров; клиентский — только клиента (активный `client_contacts.telegram_user_id`) и гостя. Админ, написавший клиентскому боту, — для него обычный гость или клиент.

### 5. Вход по приглашению

Номер телефона для входа не используется: у человека номер в Telegram может отличаться от того, что знает владелец.

- **Приглашение:**
  1. Владелец в личке со **служебным** ботом отправляет `/invite` (только админы).
  2. Бот показывает активные контакты без привязанного Telegram.
  3. Владелец выбирает контакт, бот выдаёт ссылку на **клиентский** бот: `https://t.me/<TELEGRAM_CLIENT_BOT_USERNAME>?start=inv_<токен>`.
  4. Владелец пересылает ссылку клиенту любым способом.
- **Токен:**
  - 32 случайных hex-символа, в БД только SHA-256 (`client_contacts.invite_token_hash`);
  - срок 7 дней;
  - одноразовый;
  - новое приглашение заменяет старое.
- **Вход:**
  1. `/start inv_<токен>` в клиентском боте → поиск по хэшу, проверка срока и статуса.
  2. Условная привязка: `telegram_user_id` записывается, только если поле ещё пустое, токен стирается.
  3. Клиенту клиентский бот отвечает «Здравствуйте, <клиент>» и показывает меню клиента.
  4. Служебный бот пишет в группу «Заявки» «<контакт> (<клиент>) подключил Telegram: @username». Если подключился не тот человек, владелец сразу видит.
- **Ошибки:**
  - просроченная, использованная или чужая ссылка → «Ссылка недействительна — попросите менеджера прислать новую»;
  - Telegram-аккаунт уже привязан к другому контакту → отказ с тем же текстом.
- **Смена аккаунта:** `/logout` в клиентском боте или кнопка «Отвязать» у админа в `/invite` служебного бота, затем новое приглашение.
- **Регистрация клиента вне пилота.** Клиентов заводит владелец (`docs/ops/clients.md`). Самостоятельная регистрация — позже, по образцу приглашений кабинета. `clients.status = 'pending'` остаётся в схеме для неё.

### 6. Заказ

1. Mini App `/tg/order/[clientOptionId]` (кнопка клиентского бота):
   - форма вида опции;
   - превью цены той же функцией тарифа;
   - отправка — Server Action `submitOptionOrder`.
2. Сервер:
   1. `initData` → контакт → клиент (`active`);
   2. опция принадлежит клиенту и активна;
   3. zod вида формы;
   4. время по Europe/Prague → слот;
   5. тариф → `Quote`;
   6. запись.
3. **Запись** — новая SQL-функция `public.create_option_order(...)`.
   - `security definer`, `search_path = ''`, `execute` только у `service_role`.
   - Атомарно вставляет заказ.
   - Хранит снимок: `client_id`, `client_option_id`, `contact_id`, `created_via = 'bot'`, `form_data jsonb`, `price`, `price_breakdown jsonb`, `tariff_kind`. Общие поля продублированы в колонки для списков: `from_address`, `to_address`, `scheduled_for`.
   - **Абонементы в пилот не входят:** цена всегда по тарифу опции, способ оплаты — из клиента.
4. **`orders.user_id`** перестаёт быть обязательным: у клиента из бота нет пользователя Auth. Снятие `not null` совместимо с кодом `main`.
5. **После записи** (`after()`):
   - **служебный бот** — в группу «Заявки» карточку с кнопками (ADR-0005 §4); `tg_chat_id` и `tg_message_id` сохраняются;
   - **клиентский бот** — клиенту «Заказ №N получен, ждёт подтверждения».

### 7. Статусы и уведомления

- **Переходы и кнопки** — ADR-0005 §4: «Принять», «Отклонить», «Доставлен», «Отменить». Значения `order_status` не меняются.
- **Клиенту** при «принят», «доставлен» и «отменён / отклонён» уходит:
  - сообщение **от клиентского бота**, если контакт привязан к Telegram (клиент уже нажимал `/start` по приглашению, так что бот может ему писать);
  - письмо на email контакта.

  Каждая пара «событие + канал» — строка `notifications`: идемпотентно, при сбое — кнопка повтора под карточкой в служебном боте (правило P-30). Если клиент заблокировал клиентский бот, ошибка записывается, письмо всё равно уходит.
- **Заявки с сайта:** у взятой заявки на доставку появляется кнопка «📦 Доставлено». Она переводит `leads.status` → `done` и отправляет письмо «Доставка выполнена». Письмо о взятии в работу остаётся на `client_notified_at`, как сейчас; новые события идут через `notifications`.
- **Поле времени на сайте:** `leads.delivery_at timestamptz null` (null — «как можно скорее»). Время в форме — по Праге, показывается в Telegram и в письмах.

### 8. Окружения

- **Два dev-бота** (служебный и клиентский) и тестовая группа «Заявки DEV» с dev-служебным ботом.
- **Vercel:** Production — боевые значения обоих ботов, Preview — dev-ботов. Переменные: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_ADMIN_IDS`, `TELEGRAM_CLIENT_BOT_TOKEN`, `TELEGRAM_CLIENT_WEBHOOK_SECRET`, `TELEGRAM_CLIENT_BOT_USERNAME`, `APP_URL`.
- **Вебхуки dev-ботов и адрес Mini App** — стабильный адрес ветки на Vercel. Защиту Preview Telegram проходит через Protection Bypass for Automation (секрет в параметре адреса). Боевые боты всегда на `skorouvas.cz`.
- **Адрес Mini App** в кнопках строится из env `APP_URL`: Production — `https://skorouvas.cz`, Preview — адрес ветки с параметром обхода.
- **Скрипты** `bot:webhook`, `bot:commands`, `bot:dev` принимают `--bot service|client`. Без параметра — служебный бот, как сейчас.

## Последствия

- **Плюсы.**
  - Новая услуга или тариф для клиента — строка в БД, если вид формы и тарифа уже есть.
  - Вход не зависит от номера телефона, и владелец видит каждую привязку.
  - Одна форма для бота и кабинета, одна логика цены для всех каналов.
  - Клиент видит статусы в Telegram и по почте.
- **Минусы и риски.**
  - Тарифы в `jsonb` редактируются руками. Защита — zod при расчёте и проверочный `select` в `docs/ops/clients.md`.
  - Через Telegram идёт больше персональных данных (клиенты, получатели). Риск GDPR из обсуждения 2026-10-26 растёт: у Telegram нет договора обработки данных. Владелец принимает его на пилот; до массового запуска — режим «уведомление без данных + ссылка».
  - Нужна разовая инфраструктура: два dev-бота, переменные Preview, обход защиты.
  - Два бота — два профиля, два вебхука и два набора переменных. Цена разовая; служебный поток при этом не трогается.
- **TASK-005 (кабинет)** будет переписана поверх этой модели:
  - кабинет становится вторым каналом тех же опций и форм;
  - плюс вход по приглашению, политики чтения, абонементы и привязка Telegram из кабинета.

## Отклонённые варианты

- **`client_prices` (точка × слот) из ADR-0005.** Покрывает только одну услугу с одной моделью цены.
- **Формы целиком в БД (JSON-схема).** Гибко, но бот и веб должны уметь рисовать любые поля, а валидация уходит из типизированного кода. Для одного владельца и нескольких видов услуг реестр в коде надёжнее.
- **Анкета в чате вместо Mini App.** См. §4.
- **Вход по номеру телефона** («Поделиться номером» и сверка с контактами). Не работает, когда номер в Telegram другой. Плюс нужна ручная поддержка совпадений форматов номеров.
- **Один бот для всех ролей** (первая редакция этого ADR, 2026-11-02). Пересмотрено 2026-11-05 (P-43): у клиентов должно быть своё лицо в Telegram, а служебный поток с кнопками заявок не должен меняться.
- **Оповещает нынешний бот, а заказы обрабатывает новый** (варианты А и Б в P-43). Кнопки под старыми сообщениями перестают работать. Обработка заявки уходит из группы в личку — на каждую заявку лишний шаг.
