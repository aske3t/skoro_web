# ADR-0003: Серверный путь записи и роли Supabase-клиентов

- **Статус:** принято, 2026-10-02
- **Закрывает:** P-05

## Контекст

- **В TASK-001 сложился рабочий паттерн:** Server Action + zod + admin-клиент (`server-only`) + `after()`.
- **Остальной код пишет в Supabase прямо из браузера** с publishable key. `createOrder` вызывает RPC, а слот выбирается по таймзоне браузера.
- **Впереди деньги:** единая цена (ADR-0004) и оплата. Принимать решения о цене и правах на клиенте нельзя.

## Решение

### 1. Все записи — через сервер

- **Формы** — Server Actions.
- **Внешние вызовы** (вебхуки платёжного провайдера и т. п.) — Route Handlers.
- **Из браузера в Supabase разрешено только:** чтение публичных справочников и вход/выход (Auth).

### 2. Структура доменного модуля

Эталон — `src/lib/leads/`.

- `constants.ts` — client-safe;
- `schema.ts` — zod, сервер;
- `actions.ts` — оркестратор: validate → authorize → persist → `after()`;
- чистые функции;
- тесты.

### 3. Роли клиентов

| Клиент | Ключ | Когда |
|---|---|---|
| `client.ts` | publishable | client components: справочники, Auth |
| `server.ts` | publishable + cookie | всё от имени пользователя; RLS — вторая линия защиты |
| `admin.ts` | secret, `server-only` | системные записи без пользователя и внутренние SQL-функции |

### 4. Правило admin-клиента

Перед вызовом от имени пользователя обязательны:

1. `getUser()` через server-клиент;
2. проверка прав в коде;
3. явная передача `user.id`.

Читать данные пользователя admin-клиентом нельзя, если для этого хватает server-клиента.

### 5. Транзакции

Многошаговые изменения, например заказ + списание абонемента, выполняются одной SQL-функцией. Её вызывает только сервер; `execute` закрыт для `anon` и `authenticated` (ADR-0002).

### 6. Время

Бизнес-время считается на сервере в `Europe/Prague` через `Intl` (без новых зависимостей). Время браузера используется только для отображения.

### 7. Контракт action

Action возвращает размеченное состояние (`status` + `code` + `fieldErrors` + введённые `values`), как в TASK-001. Тексты ошибок живут в UI. Неожиданные ошибки логируются на сервере, а клиенту уходит `server_error`.

## Последствия

- **`createOrder` переносится в Server Action** (TASK-005). После этого `execute` на `create_order_for_user` у `authenticated` отзывается, либо функция заменяется внутренней.
- **RLS остаётся обязательной** как второй рубеж, а не единственный.
- **Чтение справочников калькулятором** с клиента допустимо при подтверждённой RLS (аудит в TASK-002). Перенос этого чтения в RSC — по ситуации, в рамках TASK-004.

## Отклонённые варианты

- **Писать из браузера и полагаться только на RLS.** Цена и бизнес-правила оказываются в клиенте или в непрозрачном SQL. Валидацию не переиспользовать, тестировать тяжело.
- **Отдельный API-сервис.** Избыточно для одной команды и одного деплоймента.
