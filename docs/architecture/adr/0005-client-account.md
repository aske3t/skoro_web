# ADR-0005: Личный кабинет — клиенты, точки, доступ, путь заказа

- **Статус:** принято, 2026-10-31
- **Закрывает:** P-19 (часть `orders`), P-21 (частично), P-22, P-24, P-26; задаёт рамку TASK-005
- **Связано:** ADR-0002 (миграции, дополнение 2026-10-31), ADR-0003 (серверный путь записи), ADR-0004 (цены, уточнение 2026-10-31)

## Контекст

- **Кабинет не менялся с июня.** Заказ создаётся RPC `create_order_for_user` прямо из браузера. Слот выбирается по часам браузера, а о новом заказе никто не узнаёт: уведомления нет.
- **Заявки с сайта за это время стали полноценным потоком.** Адреса, получатель, фото, IČO через ARES, кнопки в Telegram, письмо клиенту (TASK-001, P-28…P-31). Кабинет должен войти в тот же поток, а не жить отдельно.
- **Решения владельца (2026-10-31):**
  - аккаунты заводит владелец, открытой регистрации нет;
  - цены клиенту назначаются индивидуально по каждой его точке, запасной вариант — цены слотов;
  - в первой версии кабинета одна доставка; переключатель «маршрут» есть, но без логики.
- **Клиенты — и компании, и частные лица** (P-31, P-42). В B2B у одной компании может быть несколько сотрудников и несколько точек.
- **Таблица `profiles` (id = пользователь Auth) существует, но не заполняется** (P-21). Абонементы, заказы и платежи привязаны к `user_id`.

## Решение

### 1. Модель: клиент → точки → пользователи

| Таблица | Что это | Кто пишет |
|---|---|---|
| `clients` | Клиент: компания (`type = company`, IČO) или частное лицо (`person`). Название, контакты, способ оплаты по умолчанию (`invoice` / `cash`), активен ли | владелец (SQL Editor по `docs/ops/clients.md`) |
| `client_locations` | Точки клиента: название, адрес, координаты (необязательно), контакт на точке | владелец |
| `client_prices` | Индивидуальные цены: `client_id`, `location_id` (null = для всех точек клиента), `slot_id`, `price` | владелец |
| `profiles.client_id` | К какому клиенту относится пользователь. Один пользователь — один клиент; у клиента может быть несколько пользователей | владелец |

- **Абонементы, заказы и платежи получают `client_id`.** Остаток абонемента общий на компанию, а не на сотрудника. `user_id` остаётся и означает «кто оформил».
- **Чтение в кабинете** идёт через server-клиент с RLS. Политики сравнивают `client_id` с `public.current_client_id()`: это `security definer`-функция, которая читает `profiles` текущего пользователя. Старые политики по `user_id` остаются до contract-шага.
- **Пользователь без `client_id`** видит в кабинете сообщение «Аккаунт ещё не подключён к компании — свяжитесь с нами», а не пустые списки.

### 2. Доступ: только по приглашению

- **Владелец приглашает пользователя** в Supabase Dashboard → Authentication → Invite user. Строки `clients` / `profiles` создаёт SQL-сниппетами из `docs/ops/clients.md`.
- **Письма Auth (приглашение, сброс пароля)** уходят через **свой SMTP — Resend** (домен `notify.skorouvas.cz` уже подтверждён). Встроенная почта Supabase шлёт только участникам команды проекта и не больше 2 писем в час — для клиентов она не годится.
- **Ссылки в письмах** строятся по схеме SSR: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=<invite|recovery>&next=/dashboard/password`. Route Handler `/auth/confirm` вызывает `verifyOtp` и перенаправляет на `next`.
- **`next` принимается только как внутренний путь:** начинается с одиночного `/`, без `//` и `\`. Это закрывает открытый редирект, известный с аудита (`/auth/callback`).
- **Пароль задаётся и меняется** на `/dashboard/password` Server Action'ом (`updateUser`).
- **«Забыли пароль?»** на `/login` — Server Action `resetPasswordForEmail`. Ответ всегда одинаковый, чтобы не раскрывать, есть ли такой аккаунт.
- **Открытой регистрации нет.** В настройках Auth отключить «Allow new users to sign up» — приглашения работают и без неё.

### 3. Путь заказа (ADR-0003)

1. **Server Action `createOrder`** (`src/lib/orders/actions.ts`):
   1. `getUser()` → `client_id` из `profiles`;
   2. zod;
   3. слот по времени **Europe/Prague** на сервере;
   4. цена через `resolveClientPrice` (ADR-0004, уточнение);
   5. запись.
2. **Запись — новая SQL-функция `public.create_client_order(...)`.**
   - `security definer`, `set search_path = ''`; `execute` только у `service_role`, вызывает её admin-клиент.
   - Атомарно: блокирует строку абонемента, проверяет остаток и `valid_until`, списывает одну доставку или ставит полную цену и `pending_payment`, вставляет заказ.
   - Старая `create_order_for_user` не трогается: её вызывает код в `main`. Её `revoke` — contract-шаг после релиза (ADR-0002, дополнение).
3. **В заказе хранится снимок:** `price`, `price_source` (`subscription` / `location` / `client` / `slot`), `contact_email`, получатель, точка, способ оплаты.
4. **После записи `after()` шлёт уведомление в Telegram** в группу «Заявки», как у заявок (`TELEGRAM_CHAT_ID`). `chat_id` и `message_id` сохраняются в заказе, чтобы сообщение можно было править.
5. **Номер заказа** — своя последовательность `orders.number`, как у `leads.number`. Клиенту показывается «Заказ №N».

### 4. Статусы и действия

Значения enum `order_status` не меняются: новое значение показалось бы пустой меткой в коде `main`.

| Статус | Метка в кабинете | Кто переводит | Как |
|---|---|---|---|
| `new` | «Ожидает подтверждения» | — | создание |
| `in_progress` | «Принят» | админ | кнопка «✅ Принять» в Telegram |
| `delivered` | «Доставлен» | админ | кнопка «📦 Доставлен» (после «Принять») |
| `cancelled` | «Отменён» | админ — «❌ Отклонить» / «Отменить»; клиент — только пока `new` | Telegram / кнопка в кабинете |

- **Все переходы — условные `update … where status = <ожидаемый>`.** Повтор нажатия или гонка дают «уже обработан», а не двойной переход.
- **Кто и когда:** `accepted_at`, `delivered_at` (колонка уже есть), `cancelled_at`, `cancelled_by` (`client` / `admin`), `handled_by_tg_id`, `handled_by_name`.
- **Отмена клиентом** правит сообщение в Telegram: «Отменён клиентом», кнопки убираются.
- **Письмо клиенту «Заказ №N принят»** уходит через Resend по правилу P-30: факт отправки в `client_notified_at`, при сбое — кнопка повтора.
- **Курьеры, их статусы («забрал», «в пути») и раздача заказов** — отдельная задача по боту, когда владелец выберет модель (пул или назначение).

### 5. Маршрут из нескольких точек — заготовка

- В форме переключатель «Одна доставка / Маршрут».
- «Маршрут» показывает пояснение «Скоро: несколько заборов и доставок в одном заказе» и ссылку на контакт. Отправка в этом режиме недоступна.
- Сервер на `routeMode = multi` отвечает кодом `multi_route_unavailable`.
- Схема БД под маршрут не создаётся: она зависит от модели цены с расстояниями (P-38, TASK-004).

## Последствия

- **Плюсы.**
  - Заказ из кабинета доходит до владельца так же, как заявка с сайта.
  - Цена и списание абонемента считаются на сервере, слот — по пражскому времени.
  - Компания с несколькими сотрудниками и точками укладывается в модель без переделки.
- **Минусы.**
  - Владелец заводит клиентов SQL-сниппетами до появления админки.
  - Нужна разовая настройка Auth в Supabase: SMTP, шаблоны, URL, запрет регистрации.
  - В Telegram попадают персональные данные получателей. Риск по GDPR, описанный 2026-10-26 (у Telegram нет договора обработки), сохраняется до режима «уведомление без данных + ссылка в админку» (бэклог).
- **Contract после релиза TASK-005:**
  - `revoke execute` у `create_order_for_user` (затем `drop`);
  - удаление старых политик по `user_id`, если все строки получили `client_id`;
  - `not null` на `orders.client_id`.

## Отклонённые варианты

- **Только `user_id`, без `clients`.** Абонемент и история не делятся между сотрудниками компании, а точкам и ценам не к чему привязываться.
- **Заказ из кабинета как заявка (`leads`).** Заявка — анонимный первый контакт без цены и абонемента. Заказ — обязательство с ценой, статусами и владельцем.
- **Свои письма-приглашения через Resend API с `generateLink`.** Больше кода, а сброс пароля всё равно требует SMTP в Auth.
- **Новые значения `order_status` сейчас.** Ломают отображение в коде `main` при общей базе. Курьерские статусы добавятся вместе с задачей по курьерам.
