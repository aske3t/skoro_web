# ADR-0002: Схема БД как код

- **Статус:** принято, 2026-10-02
- **Закрывает:** P-02

## Контекст

- **В репозитории есть только миграция `create_leads`.** Таблицы ЛК, справочники, RLS-политики, grants и RPC `create_order_for_user` существуют только в удалённой БД.
- **Безопасность ЛК держится на RLS, которую нельзя проверить по коду.** А логика цены и списания абонемента скрыта в RPC.
- **История миграций рассинхронизирована.** `leads` применена через SQL Editor, поэтому `supabase_migrations.schema_migrations` о ней не знает, и первый же `db push` упадёт.
- **Впереди задачи, которые меняют схему и деньги:** цены, заказы, оплата.

## Решение

1. **Источник истины — `supabase/migrations/`.** Таблицы, RLS, grants, функции и триггеры меняются только миграциями. SQL Editor допустим для чтения, диагностики и правки *данных*, но не схемы.
2. **Baseline (TASK-002):**
   1. `supabase link`;
   2. `supabase migration repair 20260929205817 --status applied`;
   3. `supabase db pull` — в репозиторий ложится миграция со всей остальной схемой `public`.

   Триггеры на `auth.users` проверяются и переносятся отдельно: по умолчанию `db pull` схему `auth` не берёт.
3. **Применение к удалённой БД.** Делает владелец командой `supabase db push`, чтобы история миграций велась автоматически. Исполнитель пишет файлы миграций и проверяет их, но не применяет.
4. **Проверка синхронности.** После любого изменения `supabase db diff --linked` должен быть пустым.
5. **Типы.** `src/types/database.ts` перегенерируется после каждой миграции и коммитится в том же PR. Команду из `CLAUDE.md` запускать через временный файл.
6. **Базовые правила безопасности схемы:**
   - RLS включён на всех таблицах `public`;
   - функции `security definer` объявляются с `set search_path = ''`;
   - `execute` у таких функций отозван у `public`, `anon` и `authenticated`, если прямой вызов из клиента не предусмотрен явно;
   - целевая матрица доступа — в [CURRENT.md §5](../CURRENT.md).
7. **Окружения.**
   - До TASK-006 — один проект Supabase.
   - Перед TASK-006 (оплата) заводится отдельный staging-проект, чтобы тестовые платежи и данные не смешивались с боевыми. Справочники туда переносятся сидом `supabase/seed.sql` (data-only дамп справочных таблиц).

## Последствия

- **Плюсы.**
  - Аудит RLS возможен по коду.
  - Схему можно поднять с нуля (staging, локально).
  - Изменения проходят ревью в PR.
- **Минусы.**
  - Для `db pull` и `db diff` нужен Docker.
  - Если Docker недоступен, baseline снимается `pg_dump --schema-only` из libpq по connection string и оформляется как миграция вручную.

## Отклонённые варианты

- **Оставить схему в облаке и описывать её документом.** Документ расходится с реальностью, это уже случилось.
- **Сразу заводить staging.** Это лишняя инфраструктура до появления денег в системе. Решение откладывается до TASK-006, а не отменяется.
