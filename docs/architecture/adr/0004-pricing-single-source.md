# ADR-0004: Единый источник цен

- **Статус:** принято, 2026-10-02; уточнено 2026-10-31 — источники цены, индивидуальные цены клиентов, модель с расстояниями владельца (P-35, P-38)
- **Закрывает:** P-07

## Контекст

Цена сейчас живёт в четырёх местах:

1. хардкод в `Tariffs.tsx` (240 / 180 / 150 Kč) и `Abons.tsx` (2700 / 5600 / 10800 Kč/мес.);
2. константы `surcharges.ts` и `BATCH_PER_EXTRA_STOP`, причём последняя объявлена дважды;
3. таблицы `skoro_pricing` и `delivery_slots`;
4. логика RPC `create_order_for_user`, которую не видно до baseline.

Калькулятор и заказ считают цену разными формулами. Перед гейтом оплаты это недопустимо: клиент должен платить ровно ту сумму, которую увидел.

## Решение

1. **Данные тарифов — только в БД.** Это базовые ставки, слоты, км, доп. точки, batch-правило, доплаты (вес, выкуп, доверенность) и уровни абонементов. Конкретные таблицы и колонки определяются в TASK-004.
2. **Формула — один TS-модуль `src/lib/pricing/`.**
   - Чистые функции без I/O, изоморфные, покрытые vitest.
   - Вход: `PricingData` (снимок тарифов из БД) и запрос.
   - Выход: `Quote { total, currency: "CZK", breakdown[], pricingVersion }`.
3. **Калькулятор использует модуль для мгновенного превью** на клиенте.
4. **Авторитетная цена** для заказа и оплаты считается **на сервере** тем же модулем на свежих данных из БД. Суммы, присланные клиентом, игнорируются.
5. **Заказ хранит снимок цены:** `price`, `price_breakdown` (jsonb) и версию тарифа. Это нужно для счетов и разбора споров.
6. **Атомарную запись** (заказ + списание абонемента) делает внутренняя SQL-функция. Цену она получает от сервера и сама её не считает (ADR-0003).
7. **Лендинг (`Tariffs`, `Abons`) читает цены из БД** в RSC с ISR (`revalidate`). Это возможно после статического лендинга из TASK-003.
8. **Константы `surcharges.ts`, `BATCH_PER_EXTRA_STOP` и хардкод цен в секциях удаляются.**

**Вне этого ADR:** режим compare калькулятора и таблица `retail_points` остаются как есть.

## Последствия

- **Плюсы.**
  - Цену меняют в одном месте, без деплоя.
  - Превью совпадает с суммой к оплате по построению.
  - Формула тестируется unit-тестами.
- **Минусы.**
  - Нужна миграция данных из констант в таблицы.
  - Калькулятор придётся частично переписать (TASK-004).

## Отклонённые варианты

- **Формула в SQL (RPC).** Для мгновенного превью пришлось бы либо дублировать её в TS, либо делать сетевой запрос на каждое изменение ввода. К тому же SQL хуже тестируется.
- **Формула только на клиенте.** Сумму к оплате нельзя доверять браузеру.

## Уточнение 2026-10-31

### Что изменилось с 2026-10-02

- **Ответы на открытые вопросы.**
  - 240 / 180 / 150 Kč в `Tariffs` — это слоты `delivery_slots` (Экспресс, 3 часа, в течение дня).
  - RPC `create_order_for_user` ставит цену = `base_price` слота, а при активном абонементе — 0 со списанием одной доставки.
- **Версии сайта «бизнес / частные лица»** (P-31, P-32, P-35): тарифы могут различаться по аудитории. Заготовка — `src/lib/pricing/{business,personal}.ts`, расчёта пока нет.
- **Индивидуальные цены клиентов** (решение владельца, ADR-0005): клиент кабинета получает цену по своей точке и слоту, запасной вариант — цена слота.
- **Модель владельца для маршрута** (P-38): база слота включает 1 забор, 1 доставку и до 10 км; доп. точка +100 / +70 / +60 Kč; 20 Kč за км сверх 10 с округлением вверх до 10 Kč; лимиты точек и км по слотам; потолок — не дороже отдельных заказов. Для неё нужно расстояние маршрута, а его источника пока нет.
- **Пакет архитектора от 2026-10-13 с «плоской» моделью без расстояний в репозиторий не попал и отозван.** Его заменяет этот раздел.

### Решение

1. **Три источника цены, один модуль.**

   | Источник | Где данные | Кто использует |
   |---|---|---|
   | Индивидуальная цена клиента | `client_prices` (точка × слот, или клиент × слот) | кабинет (TASK-005) |
   | Публичный тариф по аудитории | БД, модель P-38 (TASK-004) | калькулятор, форма заявки, лендинг |
   | Цена слота | `delivery_slots.base_price` | запасной вариант для обоих |

   Формулы — только в `src/lib/pricing/`: чистые функции без I/O, изоморфные, с тестами.
2. **`resolveClientPrice` (TASK-005)** — `src/lib/pricing/client.ts`.
   - Вход: слот, точка (или null), цены клиента, слоты.
   - Порядок поиска: точка × слот → клиент × слот (`location_id is null`) → `base_price` слота.
   - Выход: `{ amount, source: "location" | "client" | "slot" }`.

   Абонемент — не источник цены, а способ оплаты: его применяет SQL-функция заказа (ADR-0005 §3), `price_source = subscription`.
3. **Авторитетная цена считается на сервере.** Сумма из браузера игнорируется. Заказ хранит снимок: `price`, `price_source`.
4. **Модель P-38 — TASK-004**, после решения об источнике расстояний.
   - Кандидат — серверный Google Routes API. Это новая интеграция, ключ и стоимость.
   - Порядок «сначала все заборы» и признак «за пределами Брно» решаются там же.
   - Индивидуальные цены клиентов для маршрутов (база и доп. точка по клиенту) — тоже там.
5. **Константы `surcharges.ts` и `BATCH_PER_EXTRA_STOP`, хардкод в `Tariffs` и `Abons`** живут до TASK-004. Новых не добавлять.

### Открыто для TASK-004

- Источник расстояний и бюджет на него.
- Судьба доплат (вес, выкуп, документы) и batch-правила в модели P-38.
- Разделение публичных тарифов по аудитории в БД (колонка `audience` или отдельные таблицы).
