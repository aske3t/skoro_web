# ADR-0004: Единый источник цен

- **Статус:** принято, 2026-10-02. Модель данных уточняется в TASK-004, после baseline (ADR-0002).
- **Закрывает:** P-07

## Контекст

Цена сейчас живёт в четырёх местах:

1. хардкод в `Tariffs.tsx` (240 / 180 / 150 Kč) и `Abons.tsx` (2700 / 5600 / 10800 Kč/мес.);
2. константы `surcharges.ts` и `BATCH_PER_EXTRA_STOP`, причём последняя объявлена дважды;
3. таблицы `skoro_pricing` и `delivery_slots`;
4. логика RPC `create_order_for_user`, которую не видно до baseline.

Калькулятор и заказ считают цену разными формулами. Перед гейтом оплаты это недопустимо: клиент должен платить ровно ту сумму, которую увидел.

## Решение

1. **Данные тарифов — только в БД.** Это базовые ставки, слоты, км, доп. точки, batch-правило, доплаты (вес, выкуп, доверенность) и уровни абонементов. Конкретные таблицы и колонки определяются в TASK-004.
2. **Формула — один TS-модуль `src/lib/pricing/`.**
   - Чистые функции без I/O, изоморфные, покрытые vitest.
   - Вход: `PricingData` (снимок тарифов из БД) и запрос.
   - Выход: `Quote { total, currency: "CZK", breakdown[], pricingVersion }`.
3. **Калькулятор использует модуль для мгновенного превью** на клиенте.
4. **Авторитетная цена** для заказа и оплаты считается **на сервере** тем же модулем на свежих данных из БД. Суммы, присланные клиентом, игнорируются.
5. **Заказ хранит снимок цены:** `price`, `price_breakdown` (jsonb) и версию тарифа. Это нужно для счетов и разбора споров.
6. **Атомарную запись** (заказ + списание абонемента) делает внутренняя SQL-функция. Цену она получает от сервера и сама её не считает (ADR-0003).
7. **Лендинг (`Tariffs`, `Abons`) читает цены из БД** в RSC с ISR (`revalidate`). Это возможно после статического лендинга из TASK-003.
8. **Константы `surcharges.ts`, `BATCH_PER_EXTRA_STOP` и хардкод цен в секциях удаляются.**

**Вне этого ADR:** режим compare калькулятора и таблица `retail_points` остаются как есть.

## Последствия

- **Плюсы.**
  - Цену меняют в одном месте, без деплоя.
  - Превью совпадает с суммой к оплате по построению.
  - Формула тестируется unit-тестами.
- **Минусы.**
  - Нужна миграция данных из констант в таблицы.
  - Калькулятор придётся частично переписать (TASK-004).

## Отклонённые варианты

- **Формула в SQL (RPC).** Для мгновенного превью пришлось бы либо дублировать её в TS, либо делать сетевой запрос на каждое изменение ввода. К тому же SQL хуже тестируется.
- **Формула только на клиенте.** Сумму к оплате нельзя доверять браузеру.

## Открытые вопросы к TASK-004

- **Чему соответствуют 240 / 180 / 150 Kč в `Tariffs`** — слотам из `delivery_slots` или отдельным продуктам?
- **Что делает RPC сейчас:** считает ли она цену и по какой формуле? Расхождения с калькулятором фиксируются до переписывания.
