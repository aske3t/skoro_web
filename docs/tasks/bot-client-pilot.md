# Пилот: клиентский Telegram-бот

> Решения — [ADR-0006](../architecture/adr/0006-client-options-and-bot-orders.md) (главный документ), ADR-0005 (статусы и кнопки, §4), ADR-0003, ADR-0002 (дополнение: миграции совместимы с `main`), ADR-0004.
> Ветка: `feature/bot-clients` от `dev`. Работа итеративная: перед шагом — план без кода и «ок» владельца, после шага — проверка владельцем в dev-ботах и коммит.
> Живое описание ботов — `docs/telegram-bot.md`, обновлять после каждого шага. Отступления от ADR и вопросы — в PROPOSALS.
> **Два бота** (ADR-0006 §4, изменено 2026-11-05, P-43): **служебный** — нынешний, группа «Заявки», карточки с кнопками, `/invite`; **клиентский** — новый, только личка: вход, меню, Mini App, статусы клиенту. Общие сервер и БД. Служебный поток и кнопки под старыми заявками не должны сломаться.
> **Пилот:** два клиента, данные вносит владелец SQL-сниппетами, одна общая опция «Доставка по городу» (`city_delivery`). Клиенты входят в клиентский бот по ссылке-приглашению (ADR-0006 §5). Регистрации в пилоте нет.

## Шаг 0 — подготовка окружения

**Агент:**
- пишет `docs/ops/telegram-dev.md` — инструкцию для владельца, сверив её с актуальной документацией Vercel и Telegram;
- учит скрипты `bot:webhook`, `bot:commands`, `bot:dev` параметру `--bot service|client` (без параметра — служебный, как сейчас). Адрес вебхука берётся из `APP_URL`: служебный — `/api/telegram/dispatch`, клиентский — `/api/telegram/client`;
- делает каркас клиентского бота: `src/lib/telegram/client/` с `createClientBot()`, Route Handler `/api/telegram/client` с проверкой `TELEGRAM_CLIENT_WEBHOOK_SECRET`, `/start` с заглушкой «Бот Skoro для клиентов». Общий код — в корне `src/lib/telegram/` (ADR-0006 §4).

**⏸ Владелец по инструкции:**
1. **Два dev-бота** через @BotFather: служебный и клиентский. У клиентского выключить Allow Groups. Тестовая группа «Skoro · Заявки DEV» с dev-служебным ботом, её ID.
2. **Vercel → Deployment Protection → Protection Bypass for Automation** — секрет.
3. **Vercel → Environment Variables → Preview** (те же значения — в `.env.local`):
   - служебный dev-бот: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (группа DEV), `TELEGRAM_WEBHOOK_SECRET`;
   - клиентский dev-бот: `TELEGRAM_CLIENT_BOT_TOKEN`, `TELEGRAM_CLIENT_WEBHOOK_SECRET`, `TELEGRAM_CLIENT_BOT_USERNAME`;
   - `TELEGRAM_ADMIN_IDS` — как в проде;
   - `APP_URL` — стабильный адрес ветки `feature/bot-clients` с параметром обхода защиты.

   В Production пока только `APP_URL=https://skorouvas.cz`. Клиентский боевой бот заводится на шаге 6.
4. **Вебхуки обоих dev-ботов** — скриптом: `npm run bot:webhook -- --bot service` и `-- --bot client`.

**Проверка:**
- `/start` в обоих dev-ботах отвечает с Preview, `getWebhookInfo` у обоих без ошибок;
- тестовая заявка с Preview приходит в группу DEV от dev-служебного бота, кнопки работают;
- боевой служебный бот не тронут.

## Шаг 1 — данные и чистые модули

**1.1. Диагностика** (только `select`):

```sql
select version();
select slug, label, base_price, max_lead_minutes from public.delivery_slots order by display_order;
select payment_status, count(*) from public.orders group by 1;
```

**1.2. Миграция `<ts>_client_options.sql`** — только расширение. Состав — ADR-0006:

| Что | По ADR-0006 |
|---|---|
| `clients`, `client_contacts` (с `invite_token_hash`, `invite_expires_at`), `client_locations`, `telegram_users`, `service_options` (+ строка `city_delivery`, `form_kind = city_delivery`), `client_options` (+ триггер: уникальная опция — только своему клиенту), `notifications` | §1, §5 |
| `bot_sessions (key text primary key, value jsonb not null, updated_at timestamptz)` — хранилище `session()` grammY; ключ с префиксом бота (`client:<chat_id>`, `service:<chat_id>`) | §1, §4 |
| `orders`: колонки `client_id`, `client_option_id`, `contact_id`, `created_via` (`bot` / `web` / `admin`), `form_data jsonb`, `price_breakdown jsonb`, `tariff_kind`, `number` (своя последовательность, со сквозной нумерацией старых строк, как `leads.number`), `accepted_at`, `cancelled_at`, `cancelled_by`, `handled_by_tg_id`, `handled_by_name`, `tg_chat_id`, `tg_message_id`; `user_id` — снять `not null`; default `payment_status` → `'pending_payment'` + `check` по значениям из диагностики | §6 |
| `public.create_option_order(...)` — `security definer`, `search_path = ''`, `execute` только у `service_role`; проверки «контакт и клиент активны, опция принадлежит клиенту и активна» с кодами-исключениями | §6 |
| `leads.delivery_at timestamptz null` | §7 |

У всех новых таблиц RLS включён, политик нет, `revoke all` у `anon` и `authenticated`. Для каждого изменения существующих объектов — `git grep … origin/main -- src` и вывод в отчёт.

**1.3. Чистые модули с тестами:**
- **`lib/orders/prague-time.ts`** — `datetime-local` → момент времени по Праге. Тесты DST: 2026-03-29, 2026-10-25.
- **`lib/orders/slot.ts`** — выбор слота по пражским минутам; режим «как можно скорее» → самый срочный слот. Старый `lib/calculator/slotpicker.ts` удаляется, когда его перестанет использовать старая форма кабинета; до тех пор — не трогать.
- **`lib/pricing/tariffs/`** — реестр, `slot_table`, `flat`, zod параметров, код `tariff_invalid`.
- **`lib/options/forms/`** — реестр, `city_delivery`. Правила валидации импортируются из `lib/leads`.
- **`lib/telegram/init-data.ts`** — проверка `initData` Mini App токеном клиентского бота. Тест — на данных, подписанных тестовым токеном.
- **`lib/telegram/invite.ts`** — генерация токена, хэш, разбор `start`-параметра `inv_<токен>`, проверка срока. Тесты.

**1.4. `docs/ops/clients.md`** — SQL-сниппеты с подстановками:
- клиент;
- контакт: имя, телефон, email — email нужен для писем о статусах;
- точка;
- подключение `city_delivery` с `slot_table` (пример JSON по slug из диагностики, `byLocation` — необязательно);
- уникальная опция (пример);
- проверочный `select` «что видит клиент».

**⏸ Владелец:**
- применяет миграцию: `db push --db-url`;
- заводит двух пилотных клиентов **с разными тарифами** «Доставки по городу». Для теста контактом клиента 1 можно указать себя — приглашение потом откроешь со своего Telegram;
- агент перегенерирует типы и проверяет данные `select`-ами.

## Шаг 2 — время доставки в форме на сайте

- **`ContactForm`, блок доставки:** поле «Когда доставить» — «Как можно скорее» (по умолчанию) или «Ко времени» с `datetime-local`. Под полем — подсказка слота. Стиль формы не меняется.
- **Сервер:** zod → `leads.delivery_at` (null = как можно скорее), время по Праге.
- **Показ:** в сообщении Telegram и в письме о взятии в работу. Тесты.

## Шаг 3 — приглашения (служебный бот) и вход, меню (клиентский бот)

**Общее:**
- каждое личное обновление любого бота → upsert `telegram_users`;
- встроенный `session()` grammY с адаптером на `bot_sessions`, ключ с префиксом бота. Плагины не подключать;
- отправка сообщения от имени любого бота — общий хелпер в корне `src/lib/telegram/` (Bot API, выбор токена), без запуска второго экземпляра `Bot`.

**Служебный бот:**
- **`/invite`** (только админ, в личке), по ADR-0006 §5:
  - список активных контактов без Telegram — кнопками;
  - выбор → ссылка `https://t.me/<TELEGRAM_CLIENT_BOT_USERNAME>?start=inv_<токен>`, срок 7 дней;
  - у привязанных контактов — кнопка «Отвязать».
- **Сообщение в группу «Заявки»** — «<контакт> (<клиент>) подключил Telegram: @username» после входа клиента.
- Остальное поведение — как сейчас.

**Клиентский бот:**
- **Роль на каждое обновление:** клиент (активный `client_contacts.telegram_user_id`) или гость. Админов клиентский бот не знает.
- **`/start inv_<токен>`:**
  - условная привязка, токен стирается;
  - клиенту — «Здравствуйте, <клиент>» и меню клиента;
  - сообщение о подключении уходит через служебный бот;
  - ошибки — по ADR-0006 §5.
- **`/logout`** — клиент отвязывает себя сам.
- **Меню (reply-клавиатура):**
  - гость: «Как подключиться» (текст: попросите ссылку у менеджера) и «Связаться»;
  - клиент: «🆕 Новый заказ», «📋 Мои заказы», «👤 Профиль», «☎️ Связаться».
- **Сообщения из групп игнорируются**, даже если бота туда добавили.

**`bot:commands -- --bot client`** — команды клиентского бота. Команды служебного не меняются, кроме добавленного `/invite` для админов (scope).

## Шаг 4 — заказ через Mini App

- **Каркас `/tg/*`:**
  - layout со скриптом `telegram-web-app.js`;
  - тема из Telegram;
  - передача `initData` в Server Action;
  - свои минимальные типы WebApp, без пакетов;
  - страницы `noindex`;
  - открытие вне Telegram → «Откройте через бота».
- **«Новый заказ»** в клиентском боте → активные опции клиента кнопками `web_app` на `/tg/order/<clientOptionId>`. Если опция одна — сразу форма.
- **Форма** по `form_kind` с `form_defaults`: `city_delivery` на `AddressInput`, `PhoneInput`, `PhotoField`.
- **Превью цены** — тем же тарифом. Клиенту видны только его цены.
- **Перед отправкой — сводка.**
- **`submitOptionOrder`** — ADR-0006 §6. `initData` проверяется токеном клиентского бота.
  - Коды ошибок: `unauthorized`, `not_linked`, `client_inactive`, `option_unavailable`, `validation` (+ `fieldErrors`), `invalid_time`, `slot_past`, `slot_outside_hours`, `tariff_invalid`, `server_error`.
  - При ошибке введённые значения сохраняются.
- **После записи** (`after()`):
  - **служебный бот** — карточка заказа в группу «Заявки» с кнопками «✅ Принять / ❌ Отклонить», `tg_chat_id` и `tg_message_id` сохраняются;
  - **клиентский бот** — клиенту «Заказ №N получен»;
  - Mini App показывает экран успеха и закрывается.
- **«📋 Мои заказы»** в клиентском боте — последние 10 заказов клиента: номер, опция, когда, статус, цена.

## Шаг 5 — статусы и уведомления клиенту

- **Кнопки карточки заказа** — в служебном боте (ADR-0005 §4), только админы, условные переходы, карточка пересобирается из БД:

  | Кнопка | Переход |
  |---|---|
  | `accept` | `new → in_progress` |
  | `decline` | `new → cancelled` |
  | `deliver` | `in_progress → delivered` |
  | `cancel` | `in_progress → cancelled` |
- **Уведомления клиенту** при «принят», «доставлен» и «отменён»:
  - сообщение от **клиентского** бота, если контакт привязан;
  - письмо на email контакта (Resend, язык — как у существующих писем, P-29);
  - каждая пара «событие + канал» — строка `notifications`. При сбое под карточкой в служебном боте появляется кнопка повтора. Если клиент заблокировал клиентский бот, ошибка записывается, а письмо уходит.
- **Заявки с сайта:** у взятой заявки на доставку — кнопка «📦 Доставлено» в служебном боте → `leads.status = done` → письмо «Доставка выполнена» через `notifications`. Письмо о взятии в работу не трогать.

## Шаг 6 — запуск пилота

**Агент:**
- готовит релиз `dev` → `main` по CURRENT §8;
- незаполненные плейсхолдеры и форму подписки **скрывает**, юридических текстов не пишет;
- пишет чек-лист запуска в `docs/ops/telegram-dev.md`, включая тексты профиля клиентского бота (черновик для владельца).

**⏸ Владелец:**
- **боевой клиентский бот** через @BotFather: имя, описание, аватар Skoro, Allow Groups выключено;
- **Vercel Production:** `TELEGRAM_CLIENT_BOT_TOKEN`, `TELEGRAM_CLIENT_WEBHOOK_SECRET`, `TELEGRAM_CLIENT_BOT_USERNAME` → Redeploy после релиза;
- **релиз:** миграции применены → PR `dev` → `main` → смоук;
- **вебхук и команды** клиентского бота: `bot:webhook -- --bot client`, `bot:commands -- --bot client`. Служебный бот: только `bot:commands` (добавился `/invite`), профиль и вебхук не меняются;
- в служебном боте `/invite` → ссылки двум пилотным клиентам.

## Ограничения

- **Источник решений — ADR-0006.** Отступление — только через PROPOSALS.
- **Миграции** — только расширение, применяет владелец. **Данных клиентов нет ни в миграциях, ни в репозитории**: он публичный.
- **Новые npm-зависимости не нужны:** `grammy` уже есть, скрипт Telegram WebApp подключается тегом `<script>`.
- **Не трогать:**
  - калькулятор;
  - лендинг — кроме поля времени (шаг 2) и скрытия плейсхолдеров (шаг 6);
  - старые страницы кабинета (TASK-005 отложена);
  - поведение существующих кнопок заявок — кроме новой «Доставлено»;
  - токен, вебхук и профиль боевого служебного бота.
- **Юридические тексты не писать.** Тексты сообщений бота и писем — черновики для утверждения владельцем.
- **Перед «готово» на каждом шаге:** `tsc`, `lint`, `test`, `build`. Тесты обязательны для всех чистых модулей шага 1 и для разбора `callback_data`.

## Приёмка пилота

- [ ] **Вход:** `/invite` в служебном боте → ссылка на клиентский бот → контакт клиента 1 открывает её и видит название клиента; в группе — сообщение о подключении от служебного бота.
- [ ] **Ссылка:** повторное открытие той же ссылки (или с другого аккаунта) → «Ссылка недействительна». После «Отвязать» и нового приглашения вход снова работает.
- [ ] **Гость:** без приглашения клиентский бот показывает только «Как подключиться» и «Связаться».
- [ ] **Заказ:** клиент открывает форму «Доставки по городу» из клиентского бота, видит свою цену — у двух клиентов разную на одном слоте — и оформляет заказ. Карточка приходит в группу от служебного бота с кнопками, клиенту — подтверждение от клиентского.
- [ ] **Статусы:** «Принять» → клиенту сообщение клиентского бота и письмо «принят». «Доставлен» → «доставка выполнена». «Отклонить» → «отменён».
- [ ] **Время:** «как можно скорее» → экспресс-цена; время через 5 часов → цена «в течение дня»; время в прошлом или вне рабочих часов → понятная ошибка.
- [ ] **Сайт:** поле времени работает, время видно в Telegram. Кнопка «Доставлено» у заявки → письмо.
- [ ] **Тариф:** битый `tariff_params` в БД → клиенту понятная ошибка, админу — сообщение.
- [ ] **Безопасность:**
  - запрос в Server Action без `initData`, с подделанным или подписанным токеном служебного бота → `unauthorized`;
  - вебхук клиентского бота с секретом служебного (и наоборот) → 401.
- [ ] **Разделение ботов:**
  - кнопки под заявками, отправленными до пилота, работают;
  - клиентский бот не реагирует в группах;
  - служебный бот не показывает клиентское меню.
- [ ] **Окружения:** dev-боты и боевые боты не мешают друг другу.
